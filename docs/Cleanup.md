# Cleanup — 清理范围规则与分支操作

清理从「每组保留一件」演进为「勾选待清理 + 范围规则」。本文档定义架构、不变量与已知缺口。

## 范围规则（ScopeRule）

带参数的只读规则对象，描述「哪些文件被勾选」：

```ts
interface ScopeUnderPathRule { kind: 'underPath'; path: string } // 只选择该目录路径下的文件
type ScopeRule = ScopeUnderPathRule
```

**两段逻辑**（架构约束）：

1. **规则定义**：`useDupeStore.applyScopeRule(rule)` 把规则登记进 store 并据此重算勾选集——规则本身是纯数据，不含任何 UI 动作；
2. **规则应用**：入口（空间分析右键菜单等）= 构造规则对象 + 调用 `applyScopeRule` + 切到清理规则页。新增入口（如未来「按扩展名圈范围」）只需扩展 ScopeRule 种类，不新增动作通路。

匹配语义：Windows 路径口径、大小写不敏感、容尾分隔符、包含子目录（`path` 自身与 `path\…`）。勾选语义：**勾选 = 待清理**（删除候选），不是保留标记；与「范围外存活才删」不变量配套。手动勾选/取消仍可修改；规则重新应用时勾选集重置为规则计算结果。

## 不变量

- 压缩包内条目（`containerPath ≠ null`）永不进入勾选集，也不进入删除清单；
- **范围外存活**：一组内全部普通条目都被勾选时，执行清理整组跳过——该组不存在范围外存活副本，删光会丢失文件；跳过组数在确认弹窗预告；
- 组数据变化（扫描增量、移除目标）后 `syncChecked()` 把勾选集与现存条目对齐：范围规则生效时按规则重算，否则剔除已不存在路径；
- 清理计划只遍历**筛选后可见组**（扩展名/最小体积/路径包含）；勾选集本身跨全部组，有筛选时以确认弹窗中的实际数量为准；
- 压缩包条目不可独立清理（只能整包删除），列表中置灰、不参与勾选。

## 空间分析右键菜单

TreeList 行右键（聚合行与加载行不提供；**`容器::` 合成节点当前未屏蔽**，见「已知缺口」）：

| 菜单项 | 适用 | 行为 |
| --- | --- | --- |
| 清理该位置重复文件 | 目录 / 文件 | 应用 `underPath(path)` 规则并切到清理规则页；该位置无重复时禁用 |
| 更新该分支 | 目录 | 引擎 `refreshBranch`：单独重遍历该子树并比对，不改变目标列表 |
| 在资源管理器中打开 | 目录 / 文件 | 目录 `shell.openPath`；文件定位到所在文件夹（`showItemInFolder`） |
| 统计数据 | 目录 | 打开统计面板（体积/数量 + k-means 大小分布直方图） |

## 更新该分支（refreshBranch）

动机：用户拿到重复清单后可能在应用外手工增删文件，需要对单个子树重扫——而非整盘重扫，也不把它加进目标列表。

流程：校验路径落在某个已同步目标内且不在排除目录内 → 等移除清理收尾 → 枚举当前子树（Everything `-path`，不可用回退 fs walk）→ 与会话内该前缀条目 diff：新增登记 / 消失删除（组随之在引擎内剔除）/ 变化更新（mtime 或体积变即清空哈希重算）→ 新容器重列包内条目 → 触碰桶重哈希 → `rebuildDirs` 全量重算体积树 → 返回 `{ added, removed, updated, treeRev }` → 结尾广播一次 `scan:rev`。

- 按**当前扫描参数（草稿）**执行，可能与整盘当时的口径不同（文档化行为）；
- 执行期与其它扫描互斥（引擎 `running` 互斥，渲染层菜单在扫描/刷新中禁用）；
- 刷新期间不改变扫描状态机（仍为 `done`），`scan:group` 增量事件对渲染层放行；**树在刷新结束、`rebuildDirs` 完成后只推进一次版本**（刷新期间的 progress 事件不被渲染层消费）；
- `RefreshBranchReport` 的 `added/removed/updated` 目前只在 IPC 层返回，渲染层未展示；失败（不在目标内/排除目录/权限）被 `TreeList` 静默 catch，无 UI 反馈（见「已知缺口」）。

## 统计数据口径

- **总体积**：树节点聚合值 `rec.size`（含子树）。真实目录不含压缩包**解压后内体积**——包内条目体积只累加到 `容器::` 合成节点，包文件本身按压缩后体积计入所在目录；若对合成节点取统计则得到包内未压缩体积。
- **总文件数**：递归真实文件 + 该前缀下压缩包内的条目（包内重复条目不重复计）；
- **总文件夹数**：递归真实目录数，**不含所选目录自身**，不含 `容器::` 合成节点；
- **平均每文件体积** = 总体积 / 总文件数。**已知口径问题**：包内条目计入分母但解压体积不计入分子，压缩包较多的分支平均值偏小；
- **大小分布**：对上述文件大小（含包内条目）做 1D k-means，`k = min(10, 不同大小档数)`：分位数种子 + Lloyd 迭代（≤24 轮）、空簇按全局分位重播种、中心重合的组就地合并，返回各组中心（取整）与成员数，按中心升序；前端渲染 ≤10 柱直方图。**已知**：统计在主进程同步排序（`[...values].sort()`），极大分支（数十万文件）可能造成短暂卡顿。

## 已知缺口（2026-11-26 记录，待修）

> 下列为文档与实现差距的如实记录；修复这些缺口前，不要假设「更新该分支」能立即让清理页完全收敛。

1. **刷新后重复组不收敛**：引擎只对「消失」的条目从组中剔除（`purgeGroupsByPaths`），被刷新「内容变化」的条目旧组不会回收；同时渲染层没有「组删除」事件通路，`pruneUnderPath` 只清勾选集、不修正组列表。结果：清理页可能残留应用外已删除/已改内容的幽灵条目，刷新后立即清理存在误删风险。需要引擎广播被解散组、或提供组快照重取。
2. **刷新期间目标变化丢失同步**：`scan.syncTargets` 在刷新中只置 `pendingSync = true`，而 `refreshBranch` 完成时未消费该标记，导致刷新期间增删目标后要等下一次扫描动作才同步。
3. **容器合成节点右键未屏蔽**：`容器::` 行仍弹出菜单；「清理」得到空勾选、「更新该分支」静默空跑、「统计数据」返回 null 后面板停留在「统计中…」。
4. **刷新失败无反馈**：`TreeList` 的 `refreshBranch(...).catch(() => {})` 吞掉所有错误，界面上没有任何提示。
5. **清理与刷新无互斥**：刷新枚举期间用户仍可在清理页执行删除，可能出现读盘失败/统计错乱（概率低）。
6. **统计口径**：见上节「平均每文件体积」与主进程同步排序两点。
